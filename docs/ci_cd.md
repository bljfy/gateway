# CI/CD 规范

项目使用 GitHub Actions 实施 CI（持续集成）和 CD（持续交付与部署），工作流位于 `.github/workflows/`。建立流水线的阶段与验收节点见 [开发计划](implementation_plan.md#13-实施顺序)，依赖安装遵循 [uv 规范](dependencies.md)。

## CI

- 在 PR、推送到 `main` 和手动触发时运行。固定 uv、Python 版本和经审查的第三方 Action 提交 SHA。
- 使用 Windows 与 Linux 矩阵；支持多个 Python 版本时覆盖声明范围。按平台安装已验证的 GmSSL 原生库，受限平台记录阻塞项，不能伪装通过。
- 干净环境安装开发依赖后，执行 [编码规范](coding.md#静态检查) 的全部静态检查、[测试规范](testing.md#执行与判定) 的完整非外部端到端测试及 `git diff --check`。锁文件过期、空测试或检查失败应阻止合并。
- pytest 增加 `--junitxml=artifacts/junit.xml` 保存结果，并保存安全测试 JSON 报告及失败诊断。设置超时、并发策略和产物保留期限，保留完整诊断输出。
- 缓存按平台、Python 和锁文件区分，验收包含无缓存重建。CI 设为合并必要检查。
- PR 任务最小只读权限，不提供部署凭据，不向不可信代码开放写权限或生产密钥。

## CD

1. 版本标签 `v*` 或手动触发发布，校验标签与项目版本一致，确认同一提交 CI 已通过。PR 不部署。
2. 从该提交、锁文件及原生库清单构建一次产物，记录版本、提交 SHA、校验值和依赖信息。构建依赖使用锁定环境，运行环境排除开发依赖。
3. 在测试环境部署，用合成数据验证三程序通信、认证失败拒绝处理、健康检查和业务冒烟测试。
4. 经 GitHub Environments 生产审批后提升同一产物，不重新构建或解析依赖。用环境 Secrets 或短期身份提供凭据，生产任务最小权限并防止并发部署。
5. 部署后检查健康及业务结果，失败则停止提升并恢复上一个已验证版本。涉及持久化数据时先备份，分别验证应用回滚与数据恢复。
6. 保存发布与部署记录，支持手动选择历史产物恢复并完成回滚演练，不用浮动依赖重建旧版本替代回滚。

## 部署文档与验收

实际交付前创建 `docs/deployment.md`，明确产物格式、目标主机、原生库获取与安装、配置及密钥提供、启动停止、健康检查、部署和回滚命令。发布或恢复前先读取该文档，在用户授权范围内执行，不擅自打包、发布或运行真实外部端到端测试。

验收保留 CI 运行记录、产物校验值、测试环境结果、生产审批记录及回滚演练结果。目标环境、凭据或部署入口未就绪时记录待验收项，不将工作流建立或构建成功报告为部署完成。

参考 [uv 与 GitHub Actions 集成](https://docs.astral.sh/uv/guides/integration/github/)。
