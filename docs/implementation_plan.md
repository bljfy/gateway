# 大模型推理服务国密安全网关实现方案

状态：设计阶段。本文为拟实现方案；当前仓库尚无业务代码、依赖配置和可执行测试，文中的指标与命令均为开发目标或计划产物。

需求依据：`docs/offical_request.md`。工程约定：根目录 `AGENT.md` 与 `docs/development.md`。

## 1. 总体决策

整体使用 Python，以 GmSSL 原生密码库及其官方 Python 绑定承载密码运算。原型选择 **SM2 双向签名认证 + SM2 加密传送会话密钥材料 + SM4-GCM 报文保护**。采用预置公钥信任模式作为首版交付路径。

原型由客户端、国密安全网关和推理服务端模拟程序组成。客户端与模拟服务端直接集成安全通信模块，网关与两侧分别建立独立安全会话。客户端把安全处理封装在传输层，上层推理调用方式、请求和响应结构保持稳定。具体业务接口由原型定义，先完成普通请求响应，再扩展流式输出。

创新方向选择隐私化审计与安全状态展示：记录安全事件和聚合指标，用测试证明敏感数据不进入日志，并量化日志的性能开销。

## 3. 系统架构与安全边界

```mermaid
flowchart LR
    C[客户端：业务调用与安全通信]
    C <-->|国密安全会话 A| G[国密网关]
    G <-->|国密安全会话 B| S[推理服务端模拟程序]
    G --> L[隐私审计与聚合指标]
```

客户端、国密安全网关和推理服务端模拟程序作为三个可独立启动的程序交付。客户端负责构造业务请求、建立安全会话、发送请求及展示结果；网关负责认证、会话管理、验证后转发及审计；模拟服务端负责验证与解密请求、执行确定性模拟推理，并保护返回结果。安全通信模块属于各程序内部的公共能力。

- 会话 A 和 B 使用不同身份、会话标识、密钥及序列号。网关不把一段链路的密钥材料转交另一段。
- 网关会接触业务明文，是受信任边界中的组件。该架构不承诺绕过网关的端到端加密，也不防御受信任主机被攻陷。
- 客户端内部通过函数调用将业务数据交给安全通信模块；模拟服务端只在验证成功后调用内部推理逻辑。两段网络链路均传输受保护记录。
- 网络攻击者可观察、截获、修改、重放报文或中断连接。加密保护内容；报文长度、时序和端点地址仍可能被观察。
- 模拟服务端地址由网关配置决定，业务请求不允许提供任意目标地址，避免网关被用作任意转发入口。

| 部分 | 拟选技术 | 用途与限制 |

| 业务接口与流式输出 | Python 类型化接口、异步迭代器 | 在客户端与模拟服务端内部保持业务语义，普通响应优先实现 |

| 测试 | `pytest`、`pytest-asyncio` | 单元、集成及异常路径测试 |
| 测量 | `psutil`、单调高精度计时器 | 进程 CPU、RSS、时延与吞吐 |
| 对比基线 | Python `ssl` + OpenSSL TLS 1.3 | 采用相同应用协议和业务负载 |

GmSSL 官方 Python 绑定提供 SM2、SM4-GCM、HMAC-SM3 等接口，并依赖本机动态库；它本身不提供完整 TLS/TLCP 通信封装。[官方说明](https://github.com/GmSSL/GmSSL-Python)

第一阶段必须验证：动态库加载、密码已知答案测试、SM2 签名身份参数、密文与签名编码、GCM 标签验证、随机数接口、Windows 打包方式。锁定绑定与动态库的精确版本或提交及文件校验值，避免把不同同名 Python 包混用。若某平台未通过，先固定已验证的运行平台并在部署说明中记录。

SM2 消息签名使用支持完整消息签名的接口，明确设置 signer ID；不要直接把普通 SM3 摘要交给底层签名接口并当作完整 SM2 消息签名。具体接口以固定版本源码为准。[官方绑定源码](https://github.com/GmSSL/GmSSL-Python/blob/main/gmssl.py)

## 5. 身份及信任管理

每个通信实体具有签名身份和密钥接收身份，分别使用 SM2 密钥对，避免一个长期密钥同时承担签名和解密职责。

信任记录包含：`peer_id`、签名公钥、加密公钥、允许角色、有效期、启用状态、密钥版本。运维在带外渠道分发这些记录，首次连接不接受对端临时提供的公钥作为信任依据。身份、公钥版本和角色必须与握手内容一致。

首版采用预置公钥，因此通过“错误公钥”覆盖题目中的“证书失效或公钥错误”要求，同时增加信任记录过期与停用测试。SM2 证书模式作为后续扩展：实现 CA 链、有效期、密钥用途、端点身份和吊销策略验证后才可启用；不能只解析证书字段就视为认证完成。

私钥采用后端支持的口令加密文件格式存储，文件路径进入配置，解锁口令从受限秘密文件或操作系统秘密存储读取。限制文件 ACL，不将真实材料放入仓库、命令行或示例配置。

## 6. 安全协议

这是用于参赛原型的应用层协议设计，不宣称具备 TLS/TLCP 互操作能力。上线前需进行独立协议评审。第一版仅允许一个已配置套件：`SM2-SM4-GCM-SM3-v1`，避免未验证的算法协商与降级路径。

### 6.1 编码约定

TCP 记录采用 `4 字节无符号网络序长度 + 记录内容`。握手内容使用确定性编码：固定字段顺序、显式长度、无歧义字节表示；协议模块负责唯一编码，签名和摘要均针对相同字节串。不得直接对任意 JSON 文本签名再通过另一种序列化方式验签。

握手字段使用长度限制；身份最长 64 字节，随机挑战各 32 字节，会话标识 16 字节。接收方用密码安全随机源生成会话标识并检查当前待建立和活跃集合中的冲突。传输层长度仅用于分帧，记录中另有经过认证的头部及载荷长度。

### 6.2 会话建立

握手只处理控制数据，结束前不允许携带或转发业务明文。下面的“发起方”和“接收方”同样适用于两段链路。

1. **ClientHello**：发起方发送协议版本、唯一允许的套件、双方身份与角色、密钥版本、随机挑战 `Nc`。接收方校验格式、身份配置与访问策略。
2. **ServerHello**：接收方生成 `Ns`、`session_id`、会话期限和握手超时参数。签名覆盖 `ClientHello` 的摘要及本消息全部非签名字段，加入 `server-hello` 域标识。发起方校验固定公钥、角色、签名、套件和参数上限。
3. **ClientKey**：发起方随机生成两个独立 SM4 密钥各 16 字节、两个独立 nonce 前缀各 4 字节及一个 32 字节握手确认密钥，共 72 字节材料。用已固定的接收方 SM2 加密公钥保护该材料。发起方签名覆盖前两步握手摘要、密钥密文和 `client-key` 域标识。接收方先验签，再解密并检查长度与参数；72 字节长度还需在前置验证中确认符合后端限制。
4. **ServerFinished**：双方计算前三步完整握手消息的 SM3 摘要 `T`。接收方发送 `HMAC-SM3(K_finish, encode(server-finished, T))`，证明已经获得相同密钥材料。发起方按恒定时间方式比较 MAC。
5. **ClientFinished**：发起方返回 `HMAC-SM3(K_finish, encode(client-finished, T))`。接收方验证后才能激活会话；失败立即清理密钥和待建立状态。
6. **Ready**：接收方发送首条 SM4-GCM 保护的就绪记录，序列号为 0，载荷包含 `T`。发起方验证后进入活跃状态。接收方后续发送序列号从 1 开始，发起方首条保护记录从 0 开始。

签名包含两侧身份、角色、挑战、协议与密钥版本；MAC 使用不同域标识，防止反射和不同消息类型混淆。每个 TCP 连接仅承载一个握手实例，设置待建立数量限制和超时；历史握手因为新的挑战、会话标识及摘要不匹配而不能建立可用会话。握手确认密钥在双方完成确认后释放。

该密钥传送方式不提供前向保密：接收方长期解密私钥事后泄漏时，已录制的握手可能被解密。重新握手轮换业务密钥不能改变这个限制。若后续需要前向保密，应选择成熟实现中的临时密钥协商或标准安全协议，重新评审握手设计。

### 6.3 业务记录与认证顺序

固定头部包含：协议版本、记录类型、会话标识、方向、64 位序列号、请求标识、分片序号、结束标志、密文长度。整数使用网络序，所有字段的编码和范围由协议规范固定。

```text
nonce = 本方向 4 字节随机前缀 || uint64_be(seq)
aad   = encode(固定头部)
record = 固定头部 || SM4-GCM(key_direction, nonce, plaintext, aad, tag_len=16)
```

密钥按方向独立；同一方向的所有请求、响应、心跳、取消、关闭和错误记录共用一条递增序列，而不是每个请求重新从 0 计数。加密前原子分配序列号，进入单一发送队列并保持写入次序。发送失败即关闭会话，禁止回退或复用序列号。

TCP 接收端只接受等于当前期望值的序列号：重复、跳号、错误方向、错误会话和关闭后的记录均拒绝。先做长度和状态检查，再校验 GCM；只有校验完成才更新接收序列号、解析业务载荷和调用业务处理器。GCM 解密过程中产生的暂存明文不得提前交给下游，流式输出也必须按完整认证记录交付。

GCM nonce 不允许在同一密钥下重复。断线恢复必须建立新会话和新密钥，不恢复旧计数器或旧密钥。不能通过共享会话密钥的方式在多个进程中无协调地发包。

### 6.4 状态、超时及关闭

状态为 `NEW → HANDSHAKING → ACTIVE → DRAINING → CLOSED`；异常可进入 `FAILED`，随后清理至 `CLOSED`。业务处理仅在 `ACTIVE` 或已有请求排空的 `DRAINING` 中进行。

活跃会话有绝对寿命、空闲期限和报文数量上限，均使用单调时钟计时。两侧独立执行配置上限，不能完全信任对端给出的期限。信任记录有效期使用墙上时钟；记录时钟异常并拒绝可疑配置。

绝对密钥期限到达后禁止使用旧密钥；正在进行的流在到期前触发排空，无法按期结束时中断并返回可识别错误。优雅关闭采用经过认证的 `CLOSE` 与 `CLOSE_ACK`；断线、超时或验证失败无需等待确认即可销毁本地会话。

认证或完整性失败不返回详细密码内部原因，只返回有限的通用错误或直接断连。不得在失败后尝试用同一载荷继续调用推理服务。

## 7. 业务接口与流式转发

客户端由业务调用层与安全传输层组成。业务调用层保持原型上层推理接口，负责提示词、检索片段等请求参数和输出展示；安全传输层在内部完成认证、加密、序列管理与响应验证。模拟服务端采用相同分层，只有经过验证的业务数据才能进入模拟推理逻辑。

普通请求包含 `request_id`、操作类型、模型标识、提示词、检索片段及推理参数；响应包含对应请求标识、结果状态、模拟输出与结束标志。业务授权信息如存在，也应放入加密载荷。业务字段与安全头部分离，业务参数不能覆盖会话身份、密钥版本或上游地址。

客户端可提供 `complete(request)` 等调用入口，安全传输的引入不要求调用方自行执行密码操作，也不改变该入口的参数和返回结构。此处为原型接口设计示例；原文没有规定具体 API 路径、HTTP 协议或 SSE 格式，接入已有接口时须补充对应的兼容测试。

网关验证入站记录后，将业务请求交给出站安全会话；模拟服务端验证后执行内部函数，生成结果，再经两段安全会话返回客户端。普通请求响应是基础交付闭环。

流式输出作为扩展按以下规则实现：

- 每条安全记录最大明文 64 KiB，较大请求与响应分片传输，总量受请求预算限制。
- 模拟服务端产生带请求标识的结果分片，网关验证后重新加密转发；客户端逐条验证完成后才向业务层交付。
- 每条流包含递增分片序号和明确的结束记录，分片字段属于认证头部。缺失结束记录视为截断，不能判定为成功完成。
- 已交付部分结果后发生错误，向调用方报告流中断，禁止伪造成功结束标志。若后续映射为 SSE，需要额外处理跨块事件与 UTF-8 字符边界。
- 接收取消记录或客户端结束调用时终止关联模拟推理任务，释放队列。队列有容量上限并通过背压防止慢消费者耗尽内存。
- 不自动重试可能已经进入推理逻辑的业务请求。网络层防重放不等于业务“恰好一次”；若需要业务幂等，单独设计服务端幂等键与结果存储。

## 8. 密钥生命周期与资源管理

| 阶段 | 处理规则 |
| --- | --- |
| 生成 | 使用后端密码安全随机源，失败则终止握手，禁止使用普通伪随机数 |
| 存储 | 会话密钥只存在进程内；长期私钥加密保存，限制访问权限 |
| 使用 | 绑定会话、方向、角色和计数器；不跨会话复用 |
| 更新 | 在寿命或数量阈值前建立新会话，分配全新密钥和标识 |
| 切换 | 新请求进入新会话；旧会话仅排空已有请求，达到硬期限立即关闭 |
| 销毁 | 关闭、认证失败、超时及取消路径均清理密钥对象、缓冲区和引用 |

首版通过“重新完整握手并切换会话”实现更新，不引入复杂的原地换钥协议。轮换失败不得延长旧密钥硬期限。

尽量使用可覆盖的可变缓冲区承载密钥，减少复制，并及时覆盖可控制的缓冲区。Python 对象、临时 `bytes` 和 ctypes/原生库内部副本无法保证全部可靠清零，因此只能报告尽力清理，不能宣称密钥彻底不可恢复。若需要更强销毁保证，应把密钥操作移到支持显式清零的原生模块或硬件密码设备。

默认采用单进程异步事件循环。阻塞密码操作由受限执行器处理，密码上下文不跨任务共享。每个会话只有一个发送写入器和一个接收验证器；并发请求通过请求标识复用连接。多进程扩展时每个会话固定归属一个进程，不把密钥写入共享缓存。

## 9. 配置与隐私化审计

建议初始配置：

```toml
[crypto]
suite = "SM2-SM4-GCM-SM3-v1"
gcm_tag_bytes = 16

[session]
handshake_timeout_seconds = 5
absolute_lifetime_seconds = 1800
idle_timeout_seconds = 300
rotate_before_seconds = 60
max_records_per_direction = 1048576
max_plaintext_bytes_per_direction = 1073741824
max_active = 1000
max_pending = 100

[limits]
max_record_plaintext_bytes = 65536
max_wire_frame_bytes = 131072
max_request_body_bytes = 1048576
max_response_body_bytes = 16777216
max_inflight_requests_per_session = 16
max_queued_bytes_per_session = 1048576
request_timeout_seconds = 120

[logging]
level = "INFO"
mode = "privacy_audit"
```

这些值是待压力测试校准的初始参数。每个方向同时受报文数、累计字节数与时间限制，任一先到即停止使用该密钥；计数包括控制记录。实现前评审 GCM 使用预算、认证失败次数限制并检查所有长度边界；弱化标签长度、启用未知套件、负数期限及互相冲突的资源限制均应拒绝启动。长流请求的时间预算不得超过密钥剩余寿命。

首版只在重启时加载配置；需要修改身份或信任策略时先停止新连接、排空并重启，避免热更新造成半旧半新的安全状态。

审计使用字段白名单：事件代码、短期会话别名、请求随机标识、结果、耗时、字节数、拒绝原因类别和密钥版本。禁止记录原始请求、响应、完整网络包、密钥、认证令牌及带业务内容的异常字符串。DEBUG 同样执行白名单规则。指标标签不使用会话标识或用户身份，防止高基数与关联泄漏。

审计采用有界队列；队列已满时拒绝接纳新业务并增加失败计数，保留明确的告警路径。安全事件单独保留容量，已接纳请求的审计写入失败需在健康状态中暴露。性能模式关闭日志时只用于独立测量，不作为默认运行配置。

安全状态通过本机受控 `/metrics` 输出活跃会话数、握手成功率、完整性失败数、重放拒绝数、轮换失败数和审计队列状态；禁止将该接口公开暴露。

创新验证分两组：同一敏感样例在开发朴素日志方案与隐私审计方案中比较泄漏标记数；同一负载下比较关闭日志、隐私审计的时延、吞吐、CPU 与内存。朴素方案仅使用合成数据并限于测试环境。

## 11. 测试设计与验收

测试工具通过网络故障注入修改、复制、延迟或截断记录。模拟服务记录不含内容的调用计数，用来证明异常报文没有触发业务；不以“出现错误日志”作为唯一判定。流式相关测试仅在实现流式扩展时执行，并单独列出结果。

| 用例 | 输入/操作 | 预期判定 |
| --- | --- | --- |
| 正常通信 | 1 KB、16 KB 合成请求；普通响应，启用流式扩展时增加流式响应 | 内容一致，双向会话完成，正常关闭 |
| 密文篡改 | 翻转密文一位 | 标签失败、会话关闭、业务调用增量为 0 |
| 头部与标签篡改 | 修改请求标识、方向、长度或标签 | 拒绝处理，不产生伪成功响应 |
| 报文重放 | 原样重复已成功请求的密文 | 只执行一次业务，重复记录被拒绝 |
| 跨会话与反射 | 将旧记录放入新会话或反向发送 | 会话/方向/密钥验证失败 |
| 会话超时 | 注入可控时钟推进至空闲或绝对期限 | 后续记录被拒绝、状态释放 |
| 错误身份 | 替换公钥、签名或密钥版本 | 握手失败，不能发送业务 |
| 信任失效 | 公钥记录过期、停用或角色不匹配 | 认证失败 |
| 握手重放与修改 | 重放旧 ClientKey，修改挑战或套件 | 新摘要不匹配，无法激活 |
| 密钥确认失败 | 修改 Finished，或提前发送业务 | 会话保持不可用并清理 |
| 序列与 nonce | 并发发送、写入失败、计数上限 | 无重复 nonce，无回退，达到上限轮换或关闭 |
| 更新与销毁 | 临近期限开新会话、旧流排空、异常断线 | 密钥和标识变化，旧会话失效 |
| 流式边界 | 跨块 UTF-8、慢消费者、取消、缺失结束记录 | 字节恢复正确，背压生效，截断不判成功 |
| 资源滥用 | 超长帧、超多握手、队列满、非法编码 | 有界拒绝，内存与连接不持续增长 |
| 日志泄漏 | 在提示词、检索片段和输出插入唯一标记 | 所有级别日志及异常输出均无标记或密钥 |
| 两段链路保护 | 分别截获 A、B 流量并篡改 | 两段均无明文业务数据，异常不越过边界 |

密码单元测试使用已知答案向量、公开互操作样例及后端自测，不能只用同一函数的加解密往返证明正确。安全测试同时核查返回、状态、下游调用次数和资源清理。

每次运行生成 JSON 报告：用例编号、步骤、合成输入摘要、修改位置、预期、实际、耗时及判定。输入数据与生成种子可复用；密钥生成始终使用安全随机源，禁止为复现测试而固定生产密码随机数。报告不包含私钥或明文会话密钥。

## 12. 性能实验与公开方案对比

### 12.1 测量方法

固定硬件、操作系统、CPU 核数、Python/GmSSL/OpenSSL 版本、进程布局、日志等级及网络条件。模拟服务提供立即回显和可配置延迟两种模式；主结果使用立即回显，避免模型计算时间掩盖通信开销。

- 握手：每个方案预热后至少 100 次独立完整会话建立，建议 3 轮各 100 次。测量从安全连接开始到双方确认可发送业务；单独报告 TCP 建连、密码握手及端到端初始化时间。两段链路分别测量，并报告客户端首次业务前等待上游建连的总时间。
- 传输：使用精确 1024、16384 字节的业务载荷，响应固定同样大小；每轮至少 1000 次请求，并延长运行至不少于 30 秒以稳定 CPU 与吞吐统计。
- 并发：分别执行 1、10、50、100 并发；固定每连接在途数量，对每档记录失败率和超时数。启用流式扩展时单独测量流式吞吐。
- 时延：报告平均握手时延、P50/P95/P99、业务往返时延；启用流式扩展时增加首块时延。失败次数、失败耗时另列，避免只统计成功样本造成偏差。
- 吞吐：使用“实际成功交付业务字节 / 总测量墙上时间”，明确单向请求吞吐与双向有效吞吐；编码、头部和标签开销另报告。不得用单条吞吐的简单平均替代整体吞吐。
- CPU：按各进程 CPU 时间增量除以墙上时间统计，100% 表示占用一个逻辑核心；同步提供除以逻辑核数后的整机归一化比例。
- 内存：定间隔采样各进程 RSS，记录各自峰值及同一时刻 RSS 总和的峰值，不能把不同时间的峰值直接相加。原生库内存纳入 RSS，采样间隔与可能漏掉瞬时峰值的限制写入报告。

保存原始 CSV/JSON、环境清单和运行命令，自动生成汇总表。尚未测量前不填写数值，不承诺本方案一定比基线快。

### 12.2 TLS 1.3 基线

基线保留相同三程序拓扑、业务接口、分帧、载荷、连接池和日志配置，将两段安全传输替换为 TLS 1.3 双向认证。固定协商版本和实际密码套件，记录双方身份验证策略。完整握手测试禁用会话恢复，首版对照不使用 0-RTT。

TLS 1.3 属于公开标准；其完整握手、记录保护和 0-RTT 重放边界可据 RFC 核查，Python TLS 接入由标准库 `ssl` 提供。[RFC 8446](https://www.rfc-editor.org/rfc/rfc8446.html)、[Python ssl 文档](https://docs.python.org/3/library/ssl.html)

SM2 固定公钥与 TLS 证书认证的信任模型不完全相同，应分别记录证书验证成本与应用握手成本，不能把差异全部归因于密码算法。额外提供裸回显通信作为开销参照，但安全功能与性能正式比较对象为 TLS 1.3。

| 对比项 | 本方案预期特性 | 基线与评价方法 |
| --- | --- | --- |
| 密码算法 | 指定国密算法组合 | 记录 TLS 实际算法；避免把算法差异等同整体安全优劣 |
| 身份验证 | 固定公钥、角色与信任有效期 | 双向证书验证，说明运维差异 |
| 防篡改与重放 | GCM + 会话严格序列 | 比较标准记录保护及应用重放边界 |
| 前向保密 | 首版不提供 | 使用临时密钥协商的 TLS 1.3 完整握手作比较 |
| 上层推理接口 | 安全处理封装在程序内部传输层 | 相同调用接口与业务数据，验证请求响应语义 |
| 部署与互操作 | 需要国密动态库和专用协议 | TLS 生态成熟，记录实际部署步骤 |
| 日志与安全状态 | 白名单审计和指标 | 在同等日志策略下比较开销 |
| 性能 | 待实测 | 握手、吞吐、CPU、RSS、失败率 |

## 13. 实施顺序

| 阶段 | 主要工作 | 进入下一阶段条件 |
| --- | --- | --- |
| M0：后端验证 | 固定环境与依赖；密码向量、加载和编码验证 | 目标平台密码测试通过，依赖锁定 |
| M1：协议核心 | 唯一编码、双向认证、密钥确认、GCM、序列管理 | 单链路正常、篡改、重放及错误身份用例通过 |
| M2：业务闭环 | 客户端、网关、模拟服务端及双链路普通响应 | 请求响应一致，异常不触发下游业务 |
| M3：完整会话 | 期限、轮换、关闭、取消、限额及流式扩展 | 更新、超时和资源测试通过；启用流式扩展时增加流式边界测试 |
| M4：创新与报告 | 隐私审计、指标、安全与性能实验、TLS 对比 | 自动报告可复现、日志泄漏判定通过 |
| M5：交付复核 | 安装脚本、使用与协议文档、演示流程 | 新环境按说明运行完整测试与演示 |

建议首次开发按 M0→M1→M2 完成普通响应闭环，再完成轮换与关闭等会话能力。流式输出是本方案提出的扩展功能，原文未指定 HTTP 路径或 SSE 格式；是否加入按交付周期确定。项目中所有阶段都在独立 worktree 中实施，逻辑完整的代码、测试与文档一同提交。

最终交付包括客户端、国密安全网关和推理服务端模拟程序源代码、固定依赖与部署说明、合成数据生成器、安全测试、基准及 TLS 对比脚本、协议和配置文档、测试报告、性能报告与创新验证结果。

## 14. 开发前需要落实的决策

当前按单机三程序演示起步，协议保留跨主机部署能力。实施时需落实目标运行平台、原型上层业务接口、团队开发周期，以及是否增加证书模式与流式输出。上述选择不影响预置公钥原型的第一阶段验证。

独立安全评审重点为握手身份绑定、SM2 编码与 signer ID、GCM 验证前不释放明文、计数器并发安全、轮换硬期限及内存清理边界。确认这些基础条件后再扩展证书认证、多进程与更强的密钥存储。

## 15. 现有系统接入扩展

后续若需要接入不能修改代码的现有客户端，或没有内置本协议的真实推理平台，可以另行评估客户端代理与推理端适配器。它们用于转换已有 HTTP/SSE 等接口与安全记录协议，并保留原接口语义。

是否引入这些组件取决于实际接入对象；引入时需要明确新增部署边界、身份、接口兼容性和跨主机通信保护，并补充测试与性能测量。上述组件不计入本次三程序原型的基础交付。
